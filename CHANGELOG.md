# Changelog

This file records notable changes for library users. Dates are release dates (UTC+8).

## 2026-10-26

### Changed
- **QUIC connections now open with their configured receive credit instead of quic-go's defaults.** `QUICReceiveWindowTuning` documented a default of 8 MiB per stream and 20 MiB per connection and set only the `Max*` fields, but quic-go treats an unset `Initial*` as 512 KiB stream / 768 KiB connection. Every fresh h3, wt or masque connection therefore opened with 512 KiB of receive credit and ramped to 8 MiB as the flow window grew — and that ramp lag is where a high-RTT link pays the most, because the first window of data waits for credit it was never offered. An unset `Initial*` now inherits the corresponding `Max*`, and `config()` writes all four fields explicitly rather than relying on the zero-means-default convention. `Validate()` checks the *effective* pair, so a caller that raises only the maximum is still checked against the initial it will inherit; it also rejects two shapes the old default-mixing hid, an initial larger than its maximum (a window that cannot grow) and a connection window smaller than one stream window at either size, which lets a single stream consume all of the connection's credit and starve every other stream permanently.

### Security
- **MASQUE target resolution now fails closed.** The legacy destination resolver never returns an empty target: it substitutes `127.0.0.1:22` for TCP and `127.0.0.1:53` for UDP, for an empty *or an invalid* value. The MASQUE path consulted that already-resolved value, so a mistyped URI silently dialed the server's own localhost SSH or DNS, and a client that mistyped `X-Target` into garbage was replaced by the same loopback default. Both substitutes cleared the availability check, and over loopback they cleared the `local_only` runtime check too, so no policy stopped them — the Brutal sentinel path is guarded for exactly this reason, the MASQUE path was not. The MASQUE target now comes from `X-Target` and, failing that, the RFC 9298 URI template, and an unresolvable target returns empty and is rejected with HTTP 403 rather than substituted. Covered by thirteen cases: missing-or-garbage URI, host-without-port, out-of-range port, a garbage `X-Target` with no logical-name registry, and the positive controls that a valid address or a registered logical name still wins.

### Fixed
- **A resume data gap could be reported as a normal end of stream.** `runResumeAttempt`'s contract is that `(false, errGap)` is an unrecoverable gap and terminates the session, so the caller can abandon the lane and reconnect rather than handing the application a truncated stream. Both of its paths masked that value. The recv side called `cancel()` before the context check, which made the check report `context.Canceled` — indistinguishable from the cancel the caller itself issued — and the send side returned `(true, nil)`, the signal for a clean shutdown. Either way the caller treated a permanent gap as a normal close and the application saw a clean EOF with no way to recover. Both paths now return the gap unchanged, ahead of the context check, which is what makes the promised `(false, errGap)` reachable and lets the caller report `TunnelDeathDataGap` instead of `context.Canceled`.
- **`sessionIdleTimeout` could evict a session that was still heartbeating.** The client's maximum heartbeat period is 300 s and the server retained sessions for 60 s, so a client on the longest permitted heartbeat cadence was dropped between beats: the retention timer expired, the session was reaped, and the next heartbeat redialed. The data plane already treated the resume KEEPALIVE as a heartbeat — `serveResumeDataPlane` calls `sess.touch()` on it — so the reaper and the heartbeat were reading two different clocks. Session retention is now derived to sit well above the maximum heartbeat, and a startup WARN reports the pairing so a misconfigured operator sees it instead of watching lanes churn at a period they did not set.

- **resume/2 could report a downlink byte as delivered when the application never received it.** Both client recv loops advanced the seq watermark by the frame length unconditionally after calling `localConn.Write`, which makes no full-write promise — it is a `net.Pipe` end in tests and the caller's own conn in production, and either may return a short write. The bytes the frame carried past that point were never handed to the application, and the *next* stream resumed from a seq past the hole. No seq check can catch this, because the seq was correct; the loss is silent and permanent. The loops now write the frame to completion before advancing, and a write error rolls the watermark back. A regression test drives a writer that caps every `Write` at 21 bytes and asserts all 192 bytes arrive; with the fix reverted it reports 63.
- **Every completed h2c tunnel leaked two connection entries for the process lifetime.** `h2c` hijacks the accepted socket before handing it to `http2`, and net/http is explicit about what happens next: `setState` deregisters a conn from the server's own set on `StateHijacked`, and the conn's deferred cleanup runs `c.close()` plus `setState(StateClosed)` only when the conn was *not* hijacked. So `http.Server.Shutdown` and `Close` cannot terminate an h2c leg, and no `StateClosed` ever arrives — the tracking maps kept one entry per finished leg, and each entry pinned a whole closed `net.TCPConn`. The accepted socket is now wrapped by a listener wrapper installed in `Serve`, so net/http adopts the wrapper as its own `c.rwc` and every close on the leg — including h2c's deferred one — reports back. `ConnContext` cannot do this: it returns the wrapper to the request context only, and the conn that h2c actually closes is the raw socket net/http already holds. Separately, the tracking map is now keyed by connection identity (the endpoint pair) rather than the conn object, because a hijacked leg is reported as at least two distinct wrappers of the same socket — net/http's own conn and the `h2c.bufConn` that `http2.ServeConn` receives — and keying on the object kept one stale row per wrapper. Verified as a regression guard: disabling the listener wrap makes the drain test fail with a permanently held entry.
- **`PauseDetachedRead` could tear down the session it exists to protect.** The downlink pump carries a 5-minute read-deadline backstop, refreshed only as it approaches expiry to avoid a `SetReadDeadline` syscall per packet. But `waitActiveWriter` blocks while the pump is parked waiting for a writer to attach, so the backstop can expire during that wait; resuming without a refresh made the next `Read` fail with `i/o timeout`, which ends the pump and closes the session.
- **WebTransport uplinks resumed from the wrong offset, permanently.** Every other transport tells the client where to resume its uplink from — h2 and grpc reply with an `X-Resume-Uplink` header, and MASQUE reuses that h2 path — but WebTransport had nowhere to put it. A WT stream has no per-stream HTTP headers, and the CONNECT response headers are written once per QUIC session, while one QUIC session serves many business streams and each stream resumes from a *different* offset. So the client's `serverUplink` stayed at whatever it held from the dial and the ring replayed from there. Short of the window that is a wasted retransmit; past it the failure is permanent. The client ring is bounded by `window_kb`, and once the committed offset rolls past the ring start those bytes are gone from memory, so `ringBuffer.ReadAt` returns `errGap`, `resumeSendLoop` propagates it, and `client_resume.go` treats `(false, errGap)` as "terminate the session" — the application then sees a clean EOF with no way to recover. The HANDSHAKE-ACK payload now carries the server's committed uplink watermark, one value per stream, in the same reply slot the client already reads. It is a reply, not an echo: each side announces the offset the other should start at. An older server sends an empty payload and a client reading that keeps its own offset, which is the pre-fix behavior — the change is strictly additive in both directions.

- **`WaitClient` could hand out a transport that had just been closed — and spin for the full 10 s doing it.** `reconcile()` collects the lanes it must tear down while holding `m.mu`, then calls `bl.close()` *after* releasing it, so there is a real window in which a lane is still reachable in state `backupAlive` while its dedicated transport has already been `Closed()`. `reconcile` guards that case with `bl.IsClosed()`; the two waiters did not. They looked up the lane, saw `backupAlive`, and returned `bl.Client()` — a client on a closed transport. With no replacement lane dialed yet that also spins against the 10 s `pickClientTimeout` instead of returning. `WaitClient` and `WaitAnyClient` now skip a closed lane the way `reconcile` already did. In `WaitAnyClient` a closed lane is skipped rather than counted as failed, so it keeps waiting for `reconcile` to refill instead of failing over early.
- **`NewTokenAuthenticator` and the Brutal path read the `Authorization` header two different ways and disagreed on scheme case.** The authenticator used `strings.TrimPrefix(auth, "Bearer ")` — case-sensitive and pinned to a single space — while `brutalTokenFromHeaders` hand-rolled the same extraction a second time, so the two paths could accept different tokens for the same request. `bearerToken` now owns the extraction and both call it, so they cannot drift apart again. The scheme name matches case-insensitively: RFC 6750 section 2.1 says auth scheme tokens are case-insensitive, so `bearer` and `BEARER` authenticate exactly as `Bearer`.
- **`secureEqual` was dead code.** A hand-rolled constant-time comparator in `protocol.go` that nothing called — every real comparison in the repo goes through `subtle.ConstantTimeCompare`, including the one in the authenticator. Deleting it removes a second implementation of a security primitive that could have drifted from the one that is actually load-bearing.
- **`BenchmarkReadFrame32KB` reported a heap allocation the hot path never pays.** Every iteration built a fresh `bytes.Reader`, charging a one-off allocation to a benchmark of a path whose real callers reuse the reader. The reader is now built once and `Reset` each iteration — `Reset` is two field stores and allocates nothing.

### Operational
- **The server now warns at startup when no token is set.** An empty token is a documented default — the bare config must stay usable for local development — so it stays a valid configuration and not a validation error. But it is the difference between an authenticated tunnel and an open one: every request authenticates as one shared `"anonymous"` principal, so all clients share a session bucket, a per-principal cap and a Brutal connection group. The warning says that at startup rather than letting it look deliberate later.

### Test infrastructure
- **The shared echo server no longer swallows a bind failure.** `startEchoServer` bound TCP and UDP inside two fire-and-forget goroutines that returned on error, so on a host where another process owned the port the echo server silently never existed — and the tunnel dialed that address anyway, because the address was simply occupied. Every test then measured traffic against a foreign process and reported success. `TestConnManagerTransportResumeMatrix` hit exactly this: it hardcoded `127.0.0.1:29100`, which one developer host had handed to an unrelated download client, so all five TCP cases timed out at a deterministic 6.2s while the two UDP cases passed — TCP and UDP are separate namespaces, so only the TCP bind failed. The binds now run in the calling goroutine and fail the test.
- **A weak-network benchmark matrix now runs in CI, on a userspace link simulator.** Every earlier throughput number in this repository came from clean loopback, where delay, loss, jitter and reordering were all zero — so nothing in the suite had ever observed how the transports behave under a link they are actually deployed on. The new `weaknet_bench_test.go` injects the impairment itself: `weakNetPipe` is one direction of a simulated link, a packet pipeline that drops per-packet with a configurable probability, caps the byte rate with a token bucket, sleeps a per-packet delay plus jitter, and holds packets so a newer one overtakes an older one. The tunnel's client leg and server leg are wrapped in a two-hop proxy, so the impairment sits exactly where a real ISP link would.

  The link is simulated in userspace rather than with a kernel qdisc on purpose, and the file header documents the boundary honestly: `tc netem` cannot inject loss into a TCP leg at all — the kernel retransmitter hides packet loss from a byte stream, so a qdisc measures only retransmission cost, not what h2tunnel does under loss. Userspace injection reaches the QUIC/UDP legs at datagram granularity. Reordering is injectable on the datagram legs only: a byte-stream link sits between two `net.Conn` endpoints, and a reordered write into a TCP connection corrupts the stream, because the reordering a qdisc would do is undone by TCP reassembly below this layer. So reorder is a UDP-only knob and its profile runs only on the QUIC legs; the TCP legs run the clean and rate-capped profiles. The kernel view is not discarded — see the next bullet.

  Five profiles: `Clean_40ms`, `Capped32KiBps_10ms`, `Loss5_80ms`, `Loss10_160ms_Jitter25ms`, `Loss5_240ms_Reorder8`. The cap's delay is chosen so the RTT-limited rate at that delay is *above* the cap — at a 40 ms link an h2 leg tops out near 80 KiB/s, so a 64 KiB/s cap sits idle and cannot be distinguished from an ignored cap; at 10 ms the cap binds for real. `BenchmarkWeakNetEchoIntegrity` is the matrix, 14 subtests across the five transports. Correctness is asserted and throughput only reported: the assertion is "the echoed bytes came back intact", so a slow profile reports a low number instead of turning the build red, and a transport that cannot carry a round through a harsh link skips with the reason rather than failing. Each subtest measures a fixed 2 s wall-clock stretch instead of `b.N` iterations — a slow profile would otherwise need very few iterations to fit the budget and report a nonsense rate — then forces `b.N = 1` so bytes/sec comes out as total bytes over the stretch. A warm-up echo round runs before the clock, because a QUIC/WebTransport connection does its handshake on the first write and charging that to the measured window makes a slow first round look like a stalled link.

  Two self-checks keep the harness honest. `TestWeakNetDelayIsObserved` is deliberately **not** gated and asserts, for h2 over TCP and h3 over UDP, that the observed echo RTT is at least the injected round trip and no more than `3× + 1 s` — the lower bound proves the simulator injects delay at all (a no-op simulator would otherwise let every benchmark report clean-loopback numbers and still look green), and the upper bound catches a broken link path. The upper bound is wide because QUIC starts from the RFC 9002 1 s initial RTT estimate and warms up over the first packets, so early samples run well above the injected value; the measurement takes the median of five rather than a mean to skip those outliers on both ends. `TestWeakNetRateCapSlowsTheLeg` asserts that at the same delay the capped leg moves well under half the bytes the uncapped one does — a relative assertion, so it survives a noisy runner.

  All profiles are gated on `H2TUNNEL_WEAKNET_BENCH`, so `-bench .` never picks them up: the existing `profile` and `test-32bit` jobs both run the full benchmark sweep, and lossy QUIC under qemu-user would take minutes per subtest. Standing up one environment costs several seconds, so each profile stands up one server and shares it across every transport that dials it rather than building one per subtest. Pipe goroutines are not joined when a subtest ends and block on a channel instead; each is small and the count is bounded by the number of subtests, so the leak is inert for the life of the test binary.
- **A shared UDP proxy poisoned the MASQUE-under-loss subtest, and one skipped subtest once cost ~90 s.** The matrix originally built one proxy per profile and reused it across that profile's legs, but `udpProxy` learns its reply address from whichever datagram arrives first and the pipe goroutines are deliberately not joined: a sender left over from the previous leg latched `replyTo`, and every reply of the next client was sent to a socket nobody reads. That made MASQUE over a 5 % lossy link look an order of magnitude slower than H3 on the very same link, and eventually unable to finish a round at all. Measured in isolation MASQUE came in level with H3 — the defect was in the harness, not the transport. The proxy is now created per client through `weakNetEnv.endpoint`, and TCP got the same treatment so the two namespaces behave identically. `tcpProxy` builds a fresh link pair per accepted connection and could never have shown the symptom, which is why only the UDP legs (H3, WT, MASQUE) were ever flaky and the TCP legs never were. While there, the dial and round bounds became named constants sized against the link rather than a bare `3 m` and `90 s`: a wedged leg once cost ~90 s per skipped subtest, turning a 65 s matrix into a four-minute one.
- **The matrix had no throughput row, and three of its own instruments were broken.** Three corrections first. The serial runner counted each 4 KiB chunk twice — once at write, once at echo — so every rate it reported was exactly half the truth. The delay stage was a pool of 256 fixed workers, which made the worker count the in-flight budget: 256 workers at a 20 ms one-way delay admit about 15 MB/s, well below the bandwidth-delay product a QUIC leg wants, so the UDP legs reported 0.08 MB/s where they delivered 77. And the rate-cap bucket subtracted the requested bytes either way, driving the token balance negative, so each deficit stacked on the last and the waits grew without bound — the 32 KiB/s cap passed 1.2 MB/s. The delay stage is now a clock-driven min-heap of scheduled delivery times owned by one goroutine, which is both the leaking per-packet design and the throttling fixed pool replaced by a single design with neither: in-flight depth follows back-pressure instead of a worker count, and the bucket starts full, clamps at the burst, and pays a deficit from the future rather than letting it compound. Sequence stamping is stamp-then-increment, because `restoreOrder` looks for sequence 0 first and the first packet admitted must carry it.

  The new `BenchmarkWeakNetPipelinedThroughput` is the throughput row: a writer and a reader run concurrently over one connection, so chunks sit outstanding inside the transport. The serial variant can never see throughput — at most one chunk is in flight, so it reports `payload/RTT`, a latency ceiling, and a pipelining or flow-control change produces a byte-identical number there. Nothing in the suite could have caught such a change, because the serial benchmark is the only runner that pairs a degraded link with bytes at all. Verified bytes are the headline metric, and the bytes the writer managed to get out are reported separately as `sent`: when the writer outruns the link the two diverge, and that divergence is the back-pressure signal.

  Both runners now settle the connection before the clock. A QUIC or WebTransport connection handshakes on its first write, and quic-go opens from the RFC 9002 1 s RTT estimate, so on a 40 ms link the first round trips run at a fraction of line rate; a single warm-up round started the clock inside that transient. Warm-up now echoes until two round trips are within a factor of 3 of each other, capped at six rounds — TCP converges on the second and pays no more than two. The connection deadline is set after the warm-up, so a slow cold start cannot eat into the cushion that exists to catch a genuinely wedged round.

  The datagram rows are bounded by the OS rather than the link, and the file header now says so: the pipe's channels are sized well past the bandwidth-delay product, but the proxy's sockets are not, so the client→server write blocks once the server's UDP receive buffer is full and a clean 40 ms QUIC leg reports whatever the runner's socket buffers allow — tens of MB/s idle, a couple on a loaded runner — while the TCP legs sit at a stable ~100 MB/s because a byte-stream proxy is drained by the kernel as a stream. Read the datagram rows against each other and against their own cap and loss rows, not as a machine-wide constant and never against the TCP rows. Raising `SO_RCVBUF` would move the ceiling but only via platform socket-option code, which is disproportionate for a benchmark that reports rather than asserts.

  Two more harness fixes: a profile's loss is now a live per-packet predicate as well as a fixed fraction, which is how `TestWeakNetFlapSurvives` black-holes a link for a bounded window under existing traffic and then lets it recover; and the new test asserts survival rather than reconnection — a round trip started inside the partition cannot complete until the link returns, so the test fails if the partition knob silently no-ops. `TestWeakNetRateCapSlowsTheLeg`'s stale rationale is corrected too: it named a 40 ms link and a 64 KiB/s cap, the inverse of the 20 ms / 16 KiB/s it actually uses, and described the cap as idle when it is the binding constraint.

- **Two new CI jobs: the userspace link as a real gate, and the kernel qdisc as a supplementary view.** `weaknet` sets `H2TUNNEL_WEAKNET_BENCH=1`, first runs the two self-checks to prove the harness injects, then runs the throughput matrix; it has no `continue-on-error`, so a corrupted echo fails the merge. `weaknet-kernel` queues a real `netem delay 20ms loss 2%` qdisc on loopback and runs the existing protocol throughput benchmarks against it, then tears the qdisc down in an `if: always()` step. It is `continue-on-error` because `tc` is not present on every GitHub-hosted runner and the command is capability-probed rather than assumed — the job writes `enabled=false` and warns when `tc qdisc add` fails. Keeping the kernel view separate from the userspace one is deliberate: the two measure different things, and neither subsumes the other (see the previous bullet for why `netem` cannot exercise a TCP leg's loss path).
- **The test ranges that were actually failing are now allocated dynamically.** The backup env, the matrix server, the matrix echo target and all seven matrix client listeners reserve their ports with a `:0` bind through `reserveAddr` / `reserveBoth`: `backup_test` was failing at `27000 + seq*2`, the matrix server was panicking at `29543`, and the matrix client listeners at `29101`–`29107` had no bind check at all, so a collision there would have been silent. `reserveBoth` also reserves the UDP namespace on the same port number, because the echo server binds both and `transportAll` opens a QUIC listener beside its TCP one — TCP and UDP are independent namespaces, so a port free in only one of them still fails. The `connMgrPortBase` constant is deleted with its last user. The other fixed ranges (`e2e_test` `20000`–`22443`, `features_test` `23000`–`26443`, `heartbeat_test` `20900`–`20902`, `wt_resume_test` `29700`–`29745`) are untouched and stay latent the same way; they are not colliding on the hosts that run CI, and converting them means threading a reserved address through several multi-test env builders rather than a one-line bind.

## 2026-09-21

### Documentation
- **The reverse-proxy header contract is now written down**: README gained a "Which headers must nginx forward?" section, and the answer is that h2tunnel needs none. `proxy_pass_header` governs the response direction, where nginx passes everything through except its own `X-Accel-*` family — and h2tunnel sets `X-Accel-Buffering: no` precisely so nginx consumes and hides it, so that is the desired outcome rather than a leak. In the request direction nginx also forwards everything by default, and h2tunnel sets no `Connection` or `Upgrade` header at all (there is no WebSocket or HTTP-Upgrade transport), so the hop-by-hop stripping that most copy-pasted proxy snippets guard against is moot here. The one genuine `proxy_set_header` is `Host`, which nginx otherwise rewrites to `$proxy_host` and would break a virtual-hosted origin. The section documents the full request-header inventory as a diagnostic checklist rather than a directive list — including the sharpest trap, where a lost `X-Target` makes the server silently dial `127.0.0.1:22` or `127.0.0.1:53` instead of the intended destination — plus the optional upstream-keep-alive caveat that `proxy_keepalive` needs `proxy_set_header Connection "";`.
- **Documented which transports may sit behind nginx**: only `h2`, `h2c` and `grpc` — long-lived HTTP streaming requests. `masque` and `wt` are both CONNECT-based over QUIC/UDP and cannot be proxied upstream by nginx (`wt` asserts an HTTP/3 stream server-side, and nginx does not proxy either HTTP/3 CONNECT or h2 extended CONNECT).

### Fixed
- **`gen-nginx` no longer emits an unparseable `location` on Windows**: POSIX shells and MSYS turn a lone `/tunnel` into `C:\...\tunnel` before the binary sees it, producing `location C:/Program Files/Git/tunnel`, which nginx rejects. Drive-qualified input is now rewritten to a path form (`C:\Users\me\tunnel` → `location /Users/me/tunnel`); plain `/tunnel` input is untouched. The generated snippet also states why no forwarding directives appear in it, and carries the optional keep-alive line commented out.

## 2026-09-19

### Security hardening
- **Session IDs are bounded**: `X-Session-ID` must be 1-128 bytes after trimming. The id is a map key on every request, the unit of per-principal accounting, and is echoed back into response headers, so an oversized value was a memory-amplification and header-inflation vector that used to be paid for only after the target had already been dialed. The check now runs first; an over-long id gets HTTP 400 with `X-Resume-Error: invalid_params` and never reaches the target. `Principal.ID` stays unbounded because it comes from the embedder's own `Authenticator`, not from the peer.
- **MASQUE-TCP no longer takes its session mode from the client**: the datagram framing and the binding target are pinned to the URI-segment classification, and the classified values are written back into `X-Network`/`X-Target` before the session is prepared. Previously a `X-Network: udp` on a `connect-tcp` request created a UDP-framed session over a TCP dial, so the server read the target's byte stream as UDP packets and lost every packet boundary.
- **Shared-profile decompression is capped**: `gunzipData` reads through `io.LimitReader` at 8 MiB and rejects anything larger, so a compressed profile cannot expand without bound on a server.
- **Transport-policy rejections stop echoing the policy**: a blocked request now gets the generic body `transport forbidden by server policy`. The old body carried `err.Error()`, which named the configured allow-list — an enumeration oracle for which transports a deployment runs. The detail stays in the server log.
- **utls channel binding restored**: the `VerifyConnection` adapter now copies `TLSUnique` and `ECHAccepted`, so an embedder's channel-binding check sees the same `ConnectionState` under camouflage as under native TLS.

### Added
- **Session-table caps**: `ServerTuning.SessionMax` / `ServerTuning.SessionMaxPerPrincipal` bound concurrent resume sessions in total and per principal, so a flood of distinct (never-resumed) session ids cannot grow the table without limit. 0 selects the built-in defaults (4096 total / 256 per principal); values above the hard cap are clamped rather than rejected. CLI keys `session_max` / `session_max_per_principal` plus `H2TUNNEL_SESSION_MAX` / `H2TUNNEL_SESSION_MAX_PER_PRINCIPAL`; they are server-only fields and a client config that carries them is rejected rather than silently ignored. Both sample configs advertise them.
- **HTTP/2 concurrent-stream cap**: the h2 server now advertises `MaxConcurrentStreams = 256` alongside the existing 8 MiB/stream and 32 MiB/connection upload buffers, so a peer cannot fan out an unbounded number of concurrent streams on one connection.
- **WebTransport per-session stream cap**: 256 concurrently served streams per session. At the limit the excess stream is reset instead of queued — a queued stream only enlarges the queue a flood feeds.

### Fixed
- **A naturally dead TCP tunnel stayed in the active set, and could hang `Client.Shutdown`**: two independent root causes. First, `finishWith` only recorded the terminal error and closed `Done()`, so the removal from the active set never happened when the engine exited on its own — `finish()` now runs when the engine does. Second, and deeper, the engine could not exit at all: on a peer-driven normal end (the peer's END frame) the send loop could still be parked reading an application conn nobody closes — a read-only tunnel, or an app blocked in `Read` — so `wg.Wait()` never returned, the engine never returned, and the tunnel stayed registered for the life of the client while the application waited on a read that could never complete. A normal recv end now interrupts the send loop (and closes the request body as a backstop against a send loop parked writing into a back-pressured stream); a recv error deliberately does not, because the send loop failing on its own write is what tells the outer loop to redial rather than terminate. Verified with two negative controls: removing either half reproduces the hang.

### Known limitations
- An abandoned h2 stream (a peer that vanishes without a FIN) keeps its handler goroutine until the connection closes. It is bounded per connection by the new 256-stream cap, and the session table reaper already drops the business session after 60 s idle, so the leaked resource is one goroutine per abandoned stream; closing it would require an idle reader in the uplink hot path, and x/net exposes no read-idle knob on the server side without also killing legitimately quiet links (the default heartbeat is 25 s and can be disabled). Connection-level flooding is a reverse-proxy / WAF concern rather than a tunnel concern.
- x/net's `http2.Server` has no `MaxHeaderListSize` field, so the advertised value is the built-in default and untunable; net/http's 1 MiB total-header limit still rejects oversized headers.

### Platform compatibility
- **32-bit audit + broader ARM support**: the library and CLI now compile for `linux/386`, `linux/arm (GOARM=6)` and `windows/386`, verified per-push by a CI build gate and, since this change, by an execution job as well. The code itself needed no changes for 32-bit: all counters use the self-aligning `atomic.Int64`/`Uint64`/`Bool` types (a raw 64-bit atomic on a struct field would panic with "unaligned 64-bit atomic operation" on 32-bit platforms), there is no `unsafe` or `uintptr` arithmetic, oversized knobs such as `brutal.rate_bytes` are `uint64`, and `Atoi`-parsed knobs are all small by nature. The resume/2 frame length field is a wire-format `uint32` and is unaffected by platform bitness.
- **Fixed: the `linux_arm` release binary aborted with "illegal instruction" on ARMv6-class CPUs** (Raspberry Pi 1/Zero, older NAS/router SoCs). No `GOARM` was set, so Go defaulted to ARMv7. The arm asset is now built with `GOARM=6` — ARMv7 and 32-bit ARMv8 execute v6 code fine, so this only widens compatibility; the asset name is unchanged. `scripts/install.sh` now maps `armv6l` and `armv8l` (32-bit userland on ARMv8) to the arm binary as well.
- **32-bit is now executed, not just compiled**: a new `test-32bit` CI job runs the full suite and every benchmark on `linux/386` and `linux/arm (GOARM=6)`, the two shipped 32-bit assets. GitHub's hosted runners are 64-bit only, so the binaries run under user-mode emulation (qemu-user, driven through the go tool's `go_<goos>_<goarch>_exec` cross-exec wrapper — the runners do not mount binfmt_misc, so the kernel cannot route 32-bit ELF to qemu itself), which talks to the host kernel directly — loopback TCP/UDP and QUIC sockets behave as they would on a real 32-bit board. `-race` is skipped there: the detector plus emulation is an order of magnitude too slow to fit the job, and data-race coverage of the same code stays native on 64-bit. The emulated benchmarks are canaries rather than measurements — they exist to prove the hot paths run on a 32-bit int without truncation or misalignment faults — so their absolute values must not be compared with the native benchmark step. 32-bit coverage profiles are uploaded alongside the 64-bit one.
- **Test hardening so the suite survives emulation**: the real-target matrix's QUIC dial retry was generalized from a single retry to three attempts with a 500 ms backoff (`dialWithStarvationRetry`). A dial aborted by quic-go's default 5 s handshake-idle bound is a scheduling stall rather than a dead server, and emulated CPUs are slow enough to hit it; a genuinely dead server fails all three attempts.

## 2026-09-18

### Added
- **TCP Brutal congestion control (Linux)**: `ClientTuning.Brutal` / `ServerTuning.Brutal` (`BrutalTuning{Enabled, RateBytes, CwndGain, GroupID, Negotiate}`) switch the tunnel's TCP legs to the TCP Brutal kernel controller via `TCP_CONGESTION` + `TCP_BRUTAL_PARAMS(23301)`, packing the `<QIQ` little-endian layout (`rate_bytes`, `cwnd_gain` in tenths, `group_id`). Off by default; a non-Linux build, or a Linux kernel without `brutal` in `/proc/net/ipv4/tcp_available`, logs one WARN at startup and does nothing — the config stays valid. `CwndGain` is validated 1-1000 (0 = the 1.5x default) at construction. Applies to h2/h2c/grpc and the MASQUE-over-h2 leg, on the client's tunnel socket and the server's accepted client socket; not to the server→origin leg, the client's local listener, or any QUIC/UDP leg. The CLI mirrors it with a `brutal` section (`enabled`/`rate_bytes`/`cwnd_gain`/`group_id`/`negotiate`) plus `H2TUNNEL_BRUTAL_ENABLED`/`_RATE_BYTES`/`_CWND_GAIN`/`_GROUP_ID`/`_NEGOTIATE`, and both sample configs gain the block.
- **Bandwidth negotiation over the tunnel**: proxy protocols carry no bandwidth field, so the two sides negotiate in-band in the tunnel's own headers. No capability flag is added and no protocol version moves: the offer must go on the first request of a leg, before the client has seen any server capabilities, so a cap could never gate it — instead an older peer simply ignores the unknown headers. The client sends `X-Brutal-Offer: rate=,gain=,nonce=` and the server answers `X-Brutal-Params: rate=,gain=,group_id=,nonce=`; the effective value is the **minimum** of both sides on each axis independently (a peer that declares a gain but no rate still contributes its gain), so neither side can exceed what the other configured, and if both declare 0 only the algorithm is switched and no starving zero rate is pushed. A fresh 16-byte nonce travels in both headers and is echoed back; the client applies a reply only on a constant-time match. The nonce deliberately never enters the HMAC input — folding it in would make the group id unique per exchange and defeat grouping.
- **Explicit `_BrutalBwExchange` sentinel target**: recognized before any target substitution (bypassing the `127.0.0.1:22` default), never dials an origin and never opens a session — the handler answers the negotiation headers plus an END frame. `Client.NegotiateBrutal(ctx)` drives it from an embedder.
- **Stable connection groups under connection migration**: `group_id` is derived independently on both sides as `u64le(HMAC-SHA256(token, seed)[:8]) | 1` (bit 0 forced so 0 keeps its "no group" meaning). The seed is the new `X-Client-Group` header — a random 128-bit value generated once per client instance, so one client's primary plus standbys share one bucket and the id survives migration, falling back to `X-Session-ID` for older clients. Sockets with a shared non-zero `group_id` share `rate_bytes` as a *total* kernel-side, so adding links cannot multiply the allowance; the static `brutal.group_id` pins a specific group to merge distinct clients on purpose. Group ids are only ever returned after authentication, so an unauthenticated probe cannot enumerate the derivation. Only `rate` and `gain` cross the wire in an offer — a client-supplied `group_id` in `X-Brutal-Offer` is ignored, so a client can never claim another client's bucket.

### Known limitations
- The negotiation result reaches the **next** dial rather than the socket carrying the reply (x/net/http2 keeps no reference to the dialer's connection), so the very first leg of a process runs at the client's own declared rate. Negotiation only ever lowers the value, so it converges monotonically.
- Group derivation reads the presented token from `X-Auth-Token` or `Authorization: Bearer`. A custom `Authenticator` that reads the token from another header still authenticates the request, but the server derives no group id for it — the connection runs ungrouped and the echoed `group_id` reads as absent.
- A kernel route with locked (read-only) Brutal rules rejects both `TCP_BRUTAL_PARAMS` and `TCP_CONGESTION` with `EPERM`; h2tunnel then logs once and leaves the default controller in place.

## 2026-09-13

### Added
- **Application-layer record padding**: `ClientTuning.Padding` / `ServerTuning.Padding` configure a random record range via `PaddingTuning{MinRecordBytes, MaxRecordBytes}`; the CLI mirrors it with nested `padding.min_record_bytes` / `padding.max_record_bytes` keys and same-named env vars. Off by default; when only the minimum is given the cap automatically becomes 125% of it. Covers streamed DATA, replayed DATA, handshake, heartbeat, END, ERROR, and the UDP/MASQUE capsules — TCP/UDP target-visible business content stays unchanged across all six transports. Stream data is reshaped into records at random targets; UDP keeps message boundaries and packets above the cap are never split. This capability only constrains h2tunnel application records; it makes no promise about the size of actual IP packets — TLS, HTTP/QUIC/TCP, CDNs, MTU, and NIC offloads can still split or coalesce records.
- **MASQUE dual-carrier selection**: `ClientTuning.MasqueALPN` (CLI `masque_alpn`) — `h3` (QUIC only), `h2` (TCP extended CONNECT only), empty = auto (h3 first; a failed first dial pins h2 cross-lane, so links with blocked UDP need not wait out the QUIC timeout per connection). Server-side `transport: masque` now treats TCP and QUIC as optional stacks, with `ListenAndServe` opening both by default. ⚠️ The server needs `GODEBUG=http2xconnect=1` at process start to accept extended CONNECT over h2 (x/net reads it once in init; `//go:debug` rejects non-stdlib keys). When missing, h3 is unaffected and the h2 leg is explicitly rejected with `extended connect not supported by peer`; the CLI logs a WARN.
- **pprof**: `h2tunnel.PprofHandler()` exposes the standard net/http/pprof for embedders to mount behind their own admin boundary (the library itself binds no port); the CLI server-side `pprof` config key / `H2TUNNEL_PPROF` enables it at a given address. CI gains a `profile` job producing CPU/allocation flamegraph SVGs and top reports as the `profiles` artifact.

### Changed (internal refactors, behavior unchanged)
- **Server-side listener plan**: the anonymous `(tcp, quic bool)` of `requiredListeners` (one tuple meant both "must be provided" and "provided but unused") is replaced by `listenerPlan` — three states per stack (`unused/optional/required`) derived once from compiled transports; auto-binding, SDK validation, and test environments share `plan.bind()` (port-sharing logic now exists in one place). Fixed: a MASQUE server with only a TCP listener used to be rejected — even though MASQUE-over-h2 is exactly what it serves.
- **Request dispatch**: one `classifyTunnelRequest` produces `tunnelRequest{kind, transport, network, target}`, shared by auth/network-policy/transport-policy/events/dispatch — replacing the three-boolean handoff `isWT/isMasqueTCP/isMasqueUDP` and the triple computation of `requestTransport()`/`getRequestDestination()` per request. Fixes two real bugs along the way: MASQUE-TCP `SessionOpened` events carried an empty Transport; standards-connect-udp (the old `MUDP` entry) did not emit `AuthRejected` on a wrong token.

### Security fixes
- **Fixed: certificate verification silently bypassed (MITM) when `UtlxFingerprint` was enabled**. `utlsTLSConfig` previously copied only `ServerName`/`InsecureSkipVerify`/`RootCAs` from the user `tls.Config` into the `utls.Config`, dropping `VerifyPeerCertificate`, `VerifyConnection`, `Certificates`/`GetClientCertificate`, `MinVersion`/`MaxVersion`, and other fields. Embedders using `InsecureSkipVerify=true` + `VerifyPeerCertificate` fingerprint pinning (e.g. in-house SSH clients) would have pinning silently disabled once camouflage was enabled, accepting any certificate. The copy is now field-by-field: all trust/authn fields pass through, with `VerifyConnection` and client certs adapted via type adapters (`crypto/tls` and `utls` same-named types are not directly assignable); `CipherSuites`/`CurvePreferences` are deliberately not copied (left to the browser fingerprint preset); `ClientSessionCache` is deliberately not copied (resuming across native/utls would skip the pinning callback on resumed connections). Regression test `utls_pinning_test.go` locks `VerifyPeerCertificate` and `VerifyConnection` (with a negative control that fails if the fix is removed). The native-TLS path and the non-camouflaged branch are unaffected (they already used full `tls.Config.Clone()`).

## 2026-09-08

### Added
- **TLS fingerprint camouflage (utls)**: `ClientOptions.UtlxFingerprint` (CLI config key `utls` / env var `H2TUNNEL_UTLS`) rewrites the ClientHello of h2/grpc clients into real-browser shapes (`chrome`, `firefox`, `edge`, `safari`, `ios`, `qq`) against JA3/JA4 fingerprinting; empty default = native crypto/tls, zero behavior change. Only TCP-TLS transports take effect — h3/wt/masque TLS happens inside quic-go and cannot be injected, so misuse errors at `NewClient` (`360` is likewise rejected because its preset does not advertise h2). Bare `net.Listen` dialers and `ClientDialer` custom sockets (VPN protect) coexist with camouflage.

### Changed
- **Outbound requests now carry a browser User-Agent uniformly** (TCP/UDP resume, backup lines, WT CONNECT all covered): previously requests had no UA and Go's Transport injected `Go-http-client/2.0`, directly contradicting the camouflaged browser TLS fingerprint. The default is an Android Chrome WebView UA (with the `w2n/Android` app identifier). Server-side logging/auditing that relied on the `Go-http-client` signature must adjust.
- **Network-change self-heal suite** (effective for TCP/UDP/WT transports):
  - `ClientTuning.AutoRedial` — automatically resets and continues after redial exhaustion (16 attempts), i.e. infinite revival, fitting "stay down until the network returns"; when off, exhaustion terminates and dispatches `TunnelDied(max retries)`.
  - `ClientTuning.RedialBudget` — per-attempt dial budget (constrains stream setup + handshake only; the timer stops once ready), tightening the abandon pace during outages.
  - `Client.ForceReconnect()` — for embedders to force abandonment of the current stream and immediate redial when an OS network-change notification (NotifyAddrChange / NWPathMonitor / ConnectivityManager) arrives; session id and recovery window are preserved, invisible to the peer. Skips the passive lag of heartbeat-timeout detection.
  - The WT-UDP datagram plane gains a disconnect-redial loop (previously a stream break ended the session); the server reuses the UDP socket by session id.
- **Strongly-typed event callback system**: `Client.SetEventHandler` / `ClientOptions.EventHandler` (TunnelEstablished, TunnelDied, Reconnecting, TargetDenied); `Server.SetEventHandler` / `ServerOptions.EventHandler` (SessionOpened/Resumed/Closed, AuthRejected, TargetDenied, ReplayDropped). Callbacks dispatch on a dedicated goroutine with recovery and never block the packet-read loop.
- **Context-ified connection lifecycle**: tunnels expose `Done() <-chan struct{}` and `Err() error`; the `ClientTuning.SessionWindowBytes` comment gains a note on outage duration vs window size.
